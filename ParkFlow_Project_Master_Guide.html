🎯 2. Problem Statement & Real-World Value

The Problem

  • Manual Bottlenecks: Traditional parking relies on physical paper slips, manual fee calculations, and human attendants, causing entry/exit congestion.
  • Space Inefficiencies: Motorists circle parking floors blindly due to lack of visibility into slot availability by vehicle category.
  • Revenue Leakage: Inaccurate tracking of exact timestamps and manual cash handling leads to accounting discrepancies.

The ParkFlow Solution

  • Automated Slot Allocation: Real-time categorization of slots (AVAILABLE, OCCUPIED, MAINTENANCE) mapped against vehicle types (BIKE, CAR, TRUCK).
  • Digital Timestamped Ticketing: Millisecond-accurate digital ticket generation and tracking.
  • Dynamic Tariff Engine: Instant automated fee computation based on duration and vehicle-type hourly rates.
  • Actionable Business Intelligence: Real-time occupancy gauges, vehicle type distribution, and revenue trends powered by Recharts.

🗄️ 5. Database Design & Entity Relationships (ER Model)

[ USERS ] (id, username, email, password_hash, role) | 1 | N [ VEHICLES ] (id, license_plate, vehicle_type, owner_name, contact) | 1 | N [ PARKING_TICKETS ] (id, ticket_number, entry_time, exit_time, amount, status) | N | 1 [ PARKING_SLOTS ] (id, slot_number, slot_type, status) | N | 1 [ PARKING_FLOORS ] (id, floor_number, floor_name, capacity, status)

Key Relational Rules:

  • ParkingFloor ↔ ParkingSlot (1-to-N): Each floor has multiple designated slots. Slot numbers are unique per facility.
  • Vehicle ↔ ParkingTicket (1-to-N): A vehicle maintains complete parking history, but can have only 1 ACTIVE ticket at a time.
  • ParkingSlot ↔ ParkingTicket (1-to-N): A slot can only be linked to 1 ACTIVE ticket when marked OCCUPIED.
  • User: Supports Role-Based Access Control (ADMIN, OPERATOR, USER).

⚙️ 6. Core Business Logic & Algorithms

1. Dynamic Parking Fee Calculation Algorithm

// Duration calculation & Ceiling Rounding
long minutes = Duration.between(entryTime, exitTime).toMinutes();
long hours = minutes / 60;
if (minutes % 60 > 0 || hours == 0) {
    hours++; // Any fraction of an hour is charged as a full hour
}

// Vehicle-specific hourly tariffs
double ratePerHour = switch (vehicle.getVehicleType().toUpperCase()) {
    case "BIKE"  -> 20.0;  // ₹20/hr
    case "CAR"   -> 50.0;  // ₹50/hr
    case "TRUCK" -> 100.0; // ₹100/hr
    default      -> 30.0;
};

double totalAmount = hours * ratePerHour;

2. Vehicle Entry & Slot Allocation State Machine

Vehicle (Check if already parked) 
   → Find Available Slot matching Vehicle Type (e.g. CAR → CAR slot)
   → Slot status updated from AVAILABLE → OCCUPIED
   → Vehicle status updated to PARKED
   → New Ticket generated with status ACTIVE & Timestamped Entry

🎯 7. Top 10 Technical Interview Questions & Model Answers

Q1: Can you walk me through the end-to-end architecture of your system?
"The system follows a decoupled, three-tier architecture: A React 19 single-page application on the frontend communicates via Axios with a Spring Boot 3 REST backend. The backend implements a layered pattern (Controller → Service → Repository → Entity). All incoming requests pass through a Spring Security JWT filter. Business logic handles ticket generation, slot state changes, and tariff computation, persisting data into a TiDB Cloud MySQL database over TLS."
Q2: How did you implement security and user authentication?
"I implemented stateless JWT authentication. Passwords are encrypted using BCrypt with salt before storage. Upon successful login, the server issues an HMAC-SHA256 signed JWT containing the user identity and role. The client stores this in localStorage and sends it in the Authorization header. A custom JwtAuthenticationFilter intercepts incoming requests, validates token integrity, and populates Spring's SecurityContextHolder."
Q3: How do you prevent race conditions if two cars try to book the same slot simultaneously?
"In ParkingTicketService, slot selection and reservation are wrapped in an atomic database transaction (@Transactional). In high-concurrency enterprise setups, we utilize optimistic locking via JPA @Version columns or pessimistic row locks (SELECT FOR UPDATE) on ParkingSlot to prevent double-booking."
Q4: Why did you use TiDB Cloud instead of standard local MySQL?
"TiDB Cloud provides a serverless, MySQL 8-compatible distributed SQL database that is accessible from anywhere over secure TLS. It eliminates the need to maintain database servers on local machines, provides automatic high-availability, auto-scaling, and allowed our cloud-hosted Spring Boot backend on Render to connect seamlessly in production."
Q5: What challenges did you encounter during cloud deployment and how did you resolve them?
"Two main challenges: First, Hibernate failed to automatically detect the MySQL dialect on a fresh cloud instance without metadata; I resolved this by explicitly configuring MySQLDialect in application.properties. Second, Cross-Origin Resource Sharing (CORS) between our Vercel frontend and Render backend was resolved by configuring a dynamic CorsConfigurationSource in Spring Security allowing verified origins."
Q6: What features would you implement in Phase 2?
"1. Automatic Number Plate Recognition (ANPR) using computer vision camera feeds.
2. Razorpay/Stripe payment gateway integration for QR code-based exit payments.
3. IoT ultrasonic slot sensor integration broadcasting live states over WebSockets.
4. EV charging slot reservation with power consumption billing."
